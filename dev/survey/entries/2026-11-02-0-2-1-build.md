# Ember use survey: Record owner-reported bugs in design 0002 and build 0.2.1 (A1 to A14) with Ember

Score each area with the scale in `README.md`. An area the session did not
use gets `not used` and the line `Not used in this session.` in place of
its answers. A question with nothing to report gets `none`.

## 1. Setup and choosing workers

Score: 4

- What happened: `emb ground --json` once, then `emb choices --claim` for four runs (two flows, one read-only check run, one skill fix with no worker), each exit 0. `emb engines --json` showed all three engines connected; OpenCode was off in Settings. Every Menu row was at `ask`, so each new run needed a worker question: three pickers in total.
- What worked: the claim reply carried the full answers and menu, so no second read was needed. The `"source": "option"` field in the dry run showed plainly that the workers came from the command line, not the Menu.
- Friction: the `emb engines --json` shape was not what a one-line parser expected (the first attempt printed `None`); a second call was needed. The owner later asked whether "Ask each time" had been bypassed, because the gap check ran on the flow reviewer without that being said in the worker question.
- Skill and references: clear on claiming every run and on asking when rows are `ask`. It does not say that the flow reviewer answer also covers the gap check.
- Suggested change: none the owner wanted; the owner decided the gap check behaviour needs no change after reviewing it.

## 2. Planning and gap checks

Score: 4

- What happened: one flow plan of five tasks, `emb flow --dry-run` (exit 0, no warnings), then `emb gapcheck` in the background (exit 0, complete coverage). It found five high and 19 medium or low gaps; the owner answered each high gap and accepted the rest. The files and order changed, so a second dry run and gap check followed: three new high gaps. The second flow (three tasks) skipped the gap check on the owner's word.
- What worked: the gap check found real faults in the plan: the flow record had no plan waves, `record.py` validation would reject records missing a new field, and `runner.py` was shared by two parallel tasks.
- Friction: one high gap rested on a wrong assumption (that the Codex at-capacity notice comes as a `warning` event). Checking a real rollout file showed it is the `error` field of `task_complete`; without that check the writer would have built the wrong match. The second gap check repeated some ground of the first.
- Skill and references: `references/gap-check.md` was clear on asking each high gap separately and repeating after material changes.
- Suggested change: in `references/gap-check.md`, tell the lead to check a gap's factual premise against a live source (a log, a record file) before putting it to the owner.

## 3. Running and following work

Score: 3

- What happened: two `emb flow --start` runs and their `--watch` calls in the background, all exit 0. Flow 1 hit one lead stop (A5 not reproducible offscreen); the owner checked a test build on the desktop and the answer was `--accept`. Flow 2 ran without a stop. One `emb run --read-only` (exit 0, 8 s) gave the tray a live run for a desktop check.
- What worked: the lead stop report carried every choice with its flags; `next:` lines named the exact follow-up command each time.
- Friction: the test-build launch command was given to the owner to run from this session's shell; the build then ran inside Claude Desktop's process scope, and Claude Desktop quit at the same moment as the test build. Later, `emb merge` removed the flow worktree while the owner's test build was still running from it. Twelve eval sessions and fifteen grader agents ran outside Ember, by hand.
- Skill and references: the skill says nothing about checking a worker's GUI build on the owner's desktop: where to launch it from, or keeping its worktree until the check ends.
- Suggested change: add a short section to `references/runs.md` for desktop checks of a worker branch: launch from a terminal outside Claude Desktop, and merge only after the owner has quit the test build.

## 4. Review, merge and cleanup

Score: 4

- What happened: `verify_branch.py` on both flow branches (24 and 6 files, clean worktrees), own checks against real data (a real Codex log for A1, the flow's own record for A3), two `emb merge ... --verdict keep` (exit 0, flow branch and worktree removed), `emb cleanup` (nothing left), `emb run --close`, and `emb choices --finish` for each claim.
- What worked: `emb merge` cleaned up flow branches and task branches in one step. The review bar kept `should` findings from blocking.
- Friction: the eval run found three skill rule breaks in the merge step (verdict only in thinking, `emb merge` chained with another command, scratch files and deletions in a kept worktree). Fixing them took three rounds of edits and reruns.
- Skill and references: after the fixes, `SKILL.md` step 9 and `references/flows.md` state the verdict, single-call merge, kept worktree and worker tip rules.
- Suggested change: none beyond the fixes already merged in 0.2.1.

## Summary

- **Top friction points:**
  1. Running: a test build launched from this session's shell ran in Claude Desktop's scope, and Claude Desktop quit when it did.
  2. Desktop app: a tray click was lost when the menu went stale while open.
  3. Review: three skill rule breaks in the merge step needed three edit and rerun rounds.
  4. Planning: a high gap built on a wrong factual premise, caught only by checking a real log.
- **Efficiencies found:** checking gap premises against live files settled questions before they reached the owner; one-wave flows with no overlapping files finished in about five minutes; graders run in parallel, one per case.
- **Bugs found:**
  - Tray quit left the app running: Quit Ember clicked after a run changed state with the menu open; nothing happened; expected the app to quit (P26).
  - Busy cursor after tray Quit: Quit Ember clicked; the cursor stayed busy about 30 s after the process ended; expected it to end at once (P21, tray extension).
  - Terminal from tray without activation token: a run's terminal opened from the tray; expected focus and an immediate end to the busy cursor (A12, fixed).
  - Eval case stub already held the requested settings (`refuses-owner-setting`), fixed.
- **Overall score:** 3. The flows, gap checks and merges did their jobs, but desktop-side checks and the tray caused most of the lost time.
