# Ember use survey: Build and release Ember 0.3.0, 0.4.0 and 0.5.0

Score each area with the scale in `README.md`. An area the session did not
use gets `not used` and the line `Not used in this session.` in place of
its answers. A question with nothing to report gets `none`.

The session was long and was compacted once. Points from before the
compaction come from its summary; the rest from the session itself.

## 1. Setup and choosing workers

Score: 4

- What happened: claims `remaining-030-k8r3` (steps 2 and 3, flow A, evals) and `ui-fixes-040-q7m2`, each with `emb choices --claim`. Workers came from the saved Menu (`multi.runs_as` = `flow`, writer Codex gpt-6-astra high, reviewer Claude opus medium), passed explicitly as `--writer codex:gpt-6-astra@high --reviewer claude:opus@medium`. `emb engines --models codex --json` listed the fallback model when the owner named "GPT sol" and two Sol models existed.
- What worked: the Menu rows answered every worker question for the flows; no picker was needed for workers. The owner set a capacity fallback (retry twice, then `codex:gpt-6.1-sol@high`) once, and it applied cleanly when needed.
- Friction: `emb choices --finish remaining-030-k8r3` returned `"status": "gone"` at the end of a long run; the claim had expired while the work went on. `ui-fixes-040-q7m2` returned `gone` straight after its claim. Neither blocked anything, but the reply does not say why a claim is gone.
- Skill and references: clear that the owner's words win over the Menu. It does not say how long a claim lives or what `gone` at finish means for work already done.
- Suggested change: `emb choices --finish` on an expired claim could say "expired after <n> minutes; nothing to finish" instead of the bare `gone`, and the skill's claims reference could name the lifetime.

## 2. Planning and gap checks

Score: 3

- What happened: the steps 2 and 3 plan (11 tasks, 8 waves) needed four gap checks (`gapcheck-bc3.json`: 5 high, 13 medium, 14 low; `gapcheck-bc4.json`: 1 high, 9 medium, 16 low) before it settled. Each high gap's premise was checked against the code before it was asked (F1). `emb flow --dry-run` was rerun after each change; waves never changed after gap check 3.
- What worked: the gap checks found real faults: a plan answer the owner had given but that was never written into `after`, a nested-run rule that left a live worker invisible in the tray, the npm launcher layout (`codex` resolves to `.../@openai/codex/bin/codex.js`, checked live), and the tray menu's D-Bus item removal.
- Friction: four rounds cost about an hour of owner questions and reruns. Gap check 3 re-raised two gaps the owner had already answered (they were answered in the plan's text but not in its `after` field). The first gap answers for the stale tray click described a fix (keep detached actions alive) that could not work on D-Bus; only the third gap check exposed that.
- Skill and references: `references/flows.md` says a material change needs another dry run and gap check, which forced the fourth round after the tray fix changed approach. That was right, but the skill gives no way to gap-check only the changed task.
- Suggested change: `emb gapcheck --task <id>` to re-check one changed task against the settled rest, so a single changed answer does not re-run the whole plan.

## 3. Running and following work

Score: 2

- What happened: the 11-task flow `flow-20261103-005526-6805ed` stopped or failed six times before it ended at exit 0 with 11 of 11 merged: a pre-commit hook refusal (ruff B023) followed by Codex "Selected model is at capacity" (exit 77 and 73 in one stop); "provider error on codex; new runs halted"; the after-wave check failing on Pyrefly (exit 82); a `lead` finding on pnpm detection; and a `release-notice` stop over an order-dependent test. One correction run hit capacity on its start and on two `--send` retries (exit 73 each) and was replaced with `codex:gpt-6.1-sol@high`.
- What worked: every stop came with exact `choices` and a `next:` line; `--send` after the hook refusal retried the commit as the skill says. When a worker's sandbox could not run `git add` (read-only `.git`), Ember committed the worker's files itself (`d5746f5`, `2fb01bb`, `22015c3`), so no work was lost. `--resume` after a lead fix on the flow branch picked up exactly where it stopped.
- Friction:
  - Codex capacity errors cost about 20 minutes over the session.
  - Workers based on the flow worktree could not run `uv` (it read the sandbox-hidden parent `pyproject.toml`) and fell back to `--no-project` runs; their checks were weaker than `make check`, so the lead reran every check.
  - `emb flow --lead <flow> update-methods --drop` was refused with "task update-methods is pending; it takes no answers", so the owner's plan to split three tasks into a parallel flow could not be done.
  - Two tests that per-task reviews passed were order-dependent once more tests ran in one process; only the flow's after-wave check exposed it.
- Skill and references: `references/flows.md` covered every stop met. It does not say a worker on a nested worktree cannot run `uv`.
- Suggested change: let `--drop` (or a new `--defer`) apply to pending tasks; make the sandbox allow the parent checkout's `pyproject.toml` for runs based on a flow worktree, or document it in `references/runs.md`.

## 4. Review, merge and cleanup

Score: 3

- What happened: `verify_branch.py` ran on every worker branch and flow branch; `make check` in each worktree as the lead's own check; `emb merge` for every task branch and flow (installed 0.2.1 `emb merge` until 0.3.0); `emb cleanup --merged-into` once. A final whole-diff review subagent found a `must`: Overview reparented nested rows on every reload and moved keyboard focus. It was reproduced with the reviewer's script and fixed by a correction run.
- What worked: cleanup removed every merged task branch and worktree and reported each removal; nothing was kept by mistake. The empty-body merge rule added for 0.5.0 gave a clean changelog with no hand edit.
- Friction: per-task reviews passed changes whose cross-task effects (the reparenting, the test order) only the whole-diff review or the after-wave check found. The 0.4.0 changelog needed a hand edit because the merge body repeated the PR title. A merge eval case showed the lead deleting `__pycache__` in a worker worktree before the merge (fixed in the skill, 459cc48).
- Skill and references: the review bar applied cleanly to the final review. The skill does not ask for a whole-diff review of a multi-task flow by a reviewer other than the lead.
- Suggested change: after a flow of several tasks, run one read-only reviewer over the whole flow diff by default, with the same review bar, before the lead's merge.

## 6. Owner interaction

Score: 3

- What happened: about 40 picker questions. The owner asked for the recommendation and its reason inside each picker (saved as a memory), answered "I don't understand this question" once (the review rounds question, re-asked in plainer words), and asked "what four fixes?" once after a reply referred to work by a label they had not seen. The owner settled one case mid-build (a Finished parent with a live run keeps it shown) and switched the 0.4.0 and 0.5.0 builds to no workers.
- What worked: pickers with the recommendation first let the owner settle many gaps quickly; standing answers saved in the scratchpad let the session run unattended through two flows.
- Friction: questions that named internal labels (fix numbers, task ids) before explaining them; one question bundled two details the owner had to have unpacked.
- Skill and references: the skill says to put every decision fact inside the question, which was right; it does not warn against labels the owner has not seen.
- Suggested change: in the skill's owner-question guidance, say to name each item by what it does, never by a label coined in the session.

## 8. Speed and waiting

Score: 3

- What happened: the steps 2 and 3 flow ran about 2 hours wall time including stops; CI on each PR took 4 to 5 minutes; the full eval run took about 15 minutes plus about 2 minutes of grading; the 0.4.0 and 0.5.0 builds by the lead took about 1 hour 15 minutes each.
- What worked: evals ran in parallel with CI; the three Dependencies tasks would have run in parallel had `--drop` allowed it.
- Friction: declared overlap on `docs/reference.md` serialized the three Dependencies tasks behind the five Overview tasks, although they touched different sections.
- Skill and references: `references/flows.md` says declared overlap serializes tasks; it gives no way to declare a shared file whose sections do not overlap.
- Suggested change: allow a plan to mark a shared file as sectioned (for example `docs/reference.md#emb-deps`), so tasks that edit different sections of one document can run in the same wave.

## Summary

- **Top friction points:**
  1. Running: Codex capacity errors and the stops they caused (about 20 minutes, one model switch).
  2. Planning: four gap check rounds for one plan (about an hour).
  3. Running: workers on a flow worktree could not run `uv` or `git add`, so the lead redid every check.
  4. Speed: `docs/reference.md` overlap serialized independent tasks, and `--drop` refused pending tasks.
  5. Review: cross-task faults found only by the whole-diff review and the after-wave check.
- **Efficiencies found:** the owner's standing answers (worker fallback, stop handling) let the session run flows unattended; the whole-diff review subagent found a `must` the per-task reviews missed; running evals in parallel with CI; the empty-body merge rule.
- **Bugs found:**
  - `emb flow --lead <flow> <pending task> --drop` exits 75 ("takes no answers"); expected a way to remove a pending task.
  - The 0.3.0 update notice read the latest release from a private repository without signing in; GitHub answered 404, so no notice ever showed. Removed in 0.5.0.
  - `emb app` handed over to a running older version after an upgrade; fixed in 0.5.0.
  - `emb choices --finish` on an expired claim returns a bare `gone`.
- **Overall score:** 3. Every release shipped with its checks green and the owner's fixes held on GNOME, but the flow needed many lead and owner interventions, and two of the three releases were built by the lead without workers at the owner's choice.
