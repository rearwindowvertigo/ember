# Ember use survey: Build and release Ember 0.6.0 to 0.12.0

Score each area with the scale in `README.md`. An area the session did not
use gets `not used` and the line `Not used in this session.` in place of
its answers. A question with nothing to report gets `none`.

This entry covers the same session as the 0.3.0 to 0.5.0 entry, from the
merge of pull request 36 (2026-11-03 15:34 UTC) to 2026-11-04 01:52 UTC.
The session was compacted several times. The facts come from a subagent's
read of the full transcript, with timestamps, and from the lead's own
context after the last compaction. The lead re-checked two of them against
the transcript: 32 owner pickers, and the exit 73 at 19:43. Times are UTC.

## 1. Setup and choosing workers

Score: 4

- What happened: `emb choices --claim` for every run, `emb engines` and
  `emb choices --json` reads before worker starts. Writers and reviewers
  came from the saved Team rows. The 0.9.0 reviewer was started with an
  explicit `--model`; the 0.11.0 and 0.12.0 reviewers resolved from the
  setting.
- What worked: claims and finishes returned clean results after 0.6.0
  (`{'status': 'gone', 'was': 'none'}` at 20:10, the #45 fix). The menu
  read gave engine, model and effort in one place.
- Friction: the 0.12.0 reviewer ran on gpt-6-astra when the lead expected
  Sol (01:08: "It ran on gpt-6-astra, though, not Sol"). The saved
  Reviewer had changed earlier in the session and the lead had not
  re-read it. The lead's announce lines kept the old screen name: "Menu,
  Single runs Reviewer..." at 20:48, 23:44, 01:03, 01:07 and 01:49, after
  0.9.0 renamed Menu to Team (#61).
- Skill and references: the installed skill shows the example line
  `Team, Single tasks Writer: ...`. The lead kept using the older
  `Menu, Single runs` wording it had loaded before the rename, and did
  not reload the skill after 0.9.0 changed it.
- Suggested change: reload the skill after a release that changes it.
  Have `emb run` print the resolved
  engine, model and effort, and the row they came from, on its first
  standard-error line, so a changed setting is visible before the turn.

## 2. Planning and gap checks

Score: 3

- What happened: no `emb flow` and no `emb gapcheck` ran. The lead wrote
  most of 0.6.0 to 0.11.0 itself and briefed four Codex writers for
  0.12.0 from `assets/task-brief.md` (01:03). The gap-check code and
  skill text were changed under #62, not run.
- What worked: the four 0.12.0 briefs had no overlapping files, so the
  writers ran at the same time and all four merged.
- Friction: three brief gaps. The commit subjects were not Conventional
  Commits because each brief's first line was not (01:09), so the
  release needed a `BEGIN_COMMIT_OVERRIDE`. The briefs named "the extra
  read folder" without its path (01:14). The smoke-test brief told the
  worker to commit, and the worker reported it could not, since Ember
  commits for it (01:50).
- Skill and references: `assets/task-brief.md` says the first line is
  the commit subject and at most 72 characters, but not that it must
  follow the repository's commit convention. Its Git section gives the
  `emb run` worker the line "Do not run git. Ember commits your edits";
  the smoke-test brief was written without the template and did not use
  it.
- Suggested change: in `assets/task-brief.md`, say the first line must be
  a subject in the repository's commit convention. Use the template even
  for a test brief.

## 3. Running and following work

Score: 3

- What happened: 13 `emb run` starts (3 tray probes, 4 reviewers, 4
  writers, 2 OpenCode smoke runs) and about 28 `--send` turns. One
  non-zero exit: `codex gpt-6.1-sol · high · 21s · exit 73 · 0 files ·
  turn 3` at 19:43 with "Selected model is at capacity", and its `next:`
  line. A resend 30 seconds later passed (turn 4, 19:45).
- What worked: the `next:` line after exit 73 named the exact resend.
  Background starts with exit codes, `--screen` and `--status` behaved as
  the skill says. On 0.12.0, OpenCode 2 runs worked first time: the
  read-only run in 9 s and the editing run in 39 s.
- Friction: read-only reviewers reported `WARNING: read-only run ...
  changed src/ember/app/theme.py` (19:40) and `main.py, window.py`
  (23:45). The changes were the lead's own edits in the same worktree,
  since the reviewer's `--dir` was the lead's live worktree. The warning
  cannot tell those apart. A live OpenCode 2 harness failed with
  `bwrap: execvp .../scratchpad/oc2/bin/opencode: No such file` (01:24)
  because the sandbox hides `/tmp`; moving the test binary under home
  fixed it in under a minute.
- Skill and references: `references/runs.md` covered exit 73 and the
  resend.
- Suggested change: have a read-only run record the worktree's status at
  start and name, in the warning, whether a change could have come from
  outside the run. Say in `references/runs.md` that a reviewer should
  not use a worktree the lead is still editing.

## 4. Review, merge and cleanup

Score: 4

- What happened: four reviewer runs found 15 `must` and 9 `should`
  findings across 0.9.0 to 0.12.0, and no `lead` findings. The lead
  reverted three `must` findings on #75 by decision (00:07) and accepted
  one `should` (pagination, 01:19). `verify_branch.py` ran four times
  for 0.12.0. Four `emb merge --verdict keep --note` calls all exited 0
  with "contained in claude/0-12-0; closed ...; removed worktree". Every
  `emb run --close` returned 0.
- What worked: the reviewers found real defects, such as "The pane
  script requires `curl`" (01:18) and "Keyboard focus does not leave the
  tooltip visible" (21:10). `emb merge` closed the run and removed the
  worktree in one step, so no `emb cleanup` was needed.
- Friction: one `emb merge` without `--note` exited 64 (01:09) and cost
  seconds. The release PR for 0.12.0 listed each change 14 times,
  because Release Please applied the PR-body override to every commit of
  the merge (01:33). The lead hand-fixed the changelog, and CI reran
  (about 8.5 minutes).
- Skill and references: SKILL.md step 9 shows `--note '<verdict line>'`
  in its `emb merge` example. The lead worked from an older copy loaded
  earlier in the session, which did not have it.
- Suggested change: in `docs/releasing.md`, say that a commit override
  in a merged PR body applies to each commit of a merge commit, so the
  session branch should carry conventional subjects instead.

## 5. Panels and stand-alone gap checks

Score: 3

- What happened: one `emb panel` (22:49 to 23:02) after a `--dry-run`,
  seven members, on the desktop app's UI. Its answers produced #70 to
  #76. No stand-alone `emb gapcheck`.
- What worked: six members answered in 70 to 148 s. The summary file and
  the `next:` line led straight to comparing answers.
- Friction: the DeepSeek member took 721 s and gated the panel's 12
  minutes. It could not read the `--read` screenshots, because OpenCode
  read-only runs lose `--read` paths (#75), and it answered from text
  recognition. The owner asked twice whether it was still running
  (22:50, 22:58). The lead's parser for `emb panel --status --json`
  failed with "TypeError: 'int' object is not iterable" (22:50).
- Skill and references: `references/panels.md` was read before the
  panel and was enough to run it.
- Suggested change: show each member's elapsed time and last activity in
  `emb panel --status`, so a slow member is visible without asking. Fix
  #75.

## 6. Owner interaction

Score: 3

- What happened: 32 AskUserQuestion pickers, 9 visual mockups and 24
  design-system artifact updates. The owner chose to have every decision
  brought as a picker (19:14, 23:04, 23:36).
- What worked: pickers with mockups settled UI choices in one round
  (tooltips, limit names, rounded corners). The owner's answers on #78
  defined completion for the autonomous 0.12.0 run, and no question came
  back after that.
- Friction: several pickers needed follow-ups: "Discuss first" (18:59),
  "Can I see what each of these controls would look like?" (19:23), and
  three clarifications in a row at 22:43. The lead gave wrong #38 install
  instructions twice (17:50) and a download command without `--repo`
  (21:24). The lead told the owner Sol had no capacity errors in 7 runs
  (23:39), but Sol had exit 73 at 19:43; the count searched the wrong
  files. One reply was cut off mid-stream (16:25).
- Skill and references: none.
- Suggested change: when an owner question offers UI choices, show the
  mockup with the first picker. Before stating a count from run records,
  search the turn outcome files as well as the summary lines.

## 8. Speed and waiting

Score: 3

- What happened: seven releases in about 9 hours. CI watches took 42 s
  to about 6 minutes each. `.deb` builds took 2 to 3 minutes after each
  release merge. The longest worker turns were the #78 driver writer
  (566 s) and Dependencies writer (399 s). The 0.11.0 reviewer stayed
  open 69 minutes over 11 turns.
- What worked: running the four 0.12.0 writers at once. All four
  finished within 10 minutes of starting.
- Friction: a flaky full-suite teardown error from the update watcher
  cost about 9 minutes (18:16 to 18:25). The longest owner-picker waits
  were 409 s, 279 s, 257 s and 225 s. The panel waited 12 minutes on one
  member.
- Skill and references: none.
- Suggested change: none beyond those in areas 3 and 5.

## Summary

- **Top friction points:**
  1. Brief gaps: non-conventional commit subjects, a missing path and a
     commit instruction in a test brief (area 2). They cost a release override and a
     changelog hand fix.
  2. Wrong instructions and counts given to the owner (area 6).
  3. The slow OpenCode panel member, which could not read its
     screenshots (area 5).
  4. Read-only warnings blaming the reviewer for the lead's edits
     (area 3).
  5. The scroll-bar overlap returning (area 7).
- **Efficiencies found:** parallel writers on non-overlapping files.
  `emb merge` closing and cleaning up in one call. Asking the owner what
  completion looks like before an autonomous run.
- **Bugs found:**
  - `emb run --close` left worker child processes running (#46).
  - Dependencies: the scroll bar overlaps tiles again (#87, after #60).
  - OpenCode read-only runs cannot read `--read` paths (#75).
  - OpenCode's terminal showed its start screen (#76).
  - Dependencies showed a newest version older than the installed one
    (#79).
  - The sandbox hid the engine's own folder when a script started it
    (fixed in c3e995a).
  - A read-only run's warning names changes made outside the run (not
    filed).
- **Overall score:** 3. Every release shipped and every worker branch
  merged after review. The owner absorbed several of the lead's own
  errors, and the lead worked from skill text older than the installed
  skill.
