settled on 2026-11-02 after the 0.2.0 build: thirteen fixes for 0.2.1, the

2026-11-02. P30 and P31 come from the panel review in
`dev/survey/reviews/2026-11-02-0-2-1-build.md`.

## A. 0.2.1 fixes

Target release: 0.2.1.

A1. The Codex driver reads "Selected model is at capacity" in a turn's
output as a provider error: the turn ends with exit 73 and the run's
`next:` line, as other provider errors do.

A2. When a flow writer's turn is collected but its commit is refused by a
hook (exit 77), a `--send` answer for that task delivers the hook's error
output to the writer together with the correction file, and the turn that
follows commits the writer's fixed files. The skill's flow reference
describes this case.

A3. Overview's flow line shows the plan wave of the latest active task as
`wave <n> of <m>`. The runner's pass count appears only in the flow's
expanded details, labelled as passes.

A4. `AppContext` saves take a result callback per save, called once with
success or the save's error. The Menu's Panel card unlocks from its own
save's callback and refreshes after its own save's failure; it reads no
queue internals or message text.

A5. A label whose text can be selected with the mouse draws no line,
frame or leftover paint around or next to it, in the Engines screen and
every other screen, in the light and dark themes (P15).

A6. In the Engines screen's model list, the name, figures, Effort cell and
Use switch of a row share one vertical alignment (P16).

A7. Every model row has the same height, whether or not the model has an
Effort picker. A model with no effort shows the same empty cell for every
engine (P17).

A8. The model list's columns fit their content: the Context, price and
Effort columns sit next to the model name, and a long name is elided with
its full text in the tooltip (P18).

A9. The engine cards keep their rows level with each other: a long
version line is elided with its full text in the tooltip, or every card
reserves the same height for it (P19).

A10. The engine card's line for the sandbox check reads `Sandbox check:`
followed by its time or `not run`, so it is not read as the engine check
in the header (P20).

A11. Every skill eval case runs once after A1 to A10, before the 0.2.1
release pull request merges (P12).

A12. When a tray menu item opens a run's terminal, Ember starts the
terminal with `XDG_ACTIVATION_TOKEN` set to the token the tray extension
provided for that click, and uses each token once (P22).

A13. A flow task's stop reason built from a run's error output leaves out
the run core's `next:` and `owner:` lines (P23).

A14. In an `ElidedLabel`, the selection highlight covers only the shown
characters the selection spans; a selection that runs into the elided part
highlights the ellipsis (P24).

## B. Flows

Target release: 0.3.0.

B1. `emb flow --cancel <flow> [--reason <text>]` stops the flow's runner,
closes no task run with `--force`, keeps every task branch and the flow
branch, records the flow as `cancelled` with the reason, and prints each
kept branch. A cancelled flow can be resumed with `--resume`.

B2. The skill lets Claude cancel a flow for any reason it states, and has
Claude report the cancel to the owner with the reason and every kept
branch.

## C. Panels

Target release: 0.3.0.

C1. `emb panel --retry <panel> <member>` starts one new read-only run for
a member whose outcome is failed, stalled, timed out or interrupted, and
adds its answer to `summary.md` and the panel record.

C2. `emb panel --close <panel>` closes every member run that is still open,
without `--force`, and reports each close and each refusal.

## D. Desktop app

Target release: 0.3.0.

D1. The tray's live state and its menu include running flows and panels.

D2. The Overview sidebar count includes flows and panels waiting for the
lead.

D3. The Flows and Panels cards have buttons that open `summary.md`, a
flow's briefs and its check logs in the desktop's default viewer.

D4. The Dependencies screen shows when a newer Ember release exists on
GitHub, with its version and download link. Ember does not install it.

D5. `emb deps` and the Dependencies screen list the `ember` skill link as a
component: current when `emb skill status` reports `installed`, and
otherwise its state with `emb skill install` (or `emb skill install
--force` for another link) as the command.

D6. Overview has two sections, Live and Finished, in place of its Flows,
Panels, Live and Finished sections. Live lists every run, flow and panel
that is starting, running or waiting for the lead. Finished lists every
ended run, flow and panel, newest first by end time, capped at 20 (P25).

D7. Every row's status chip is one of six statuses, each with its own
colour:

| Status | Covers | Colour |
|---|---|---|
| Starting | a run's or flow's `starting` | grey |
| Running | `running`, a flow's `checking` | blue |
| Waiting for Claude | a run's `waiting`, a flow's `stopped` | amber |
| Done | a run's `closed`, a flow's or panel's `done` | green |
| Incomplete | a panel's `incomplete` | a sixth tone added to the theme |
| Failed | `failed`, a gone runner or panel process | red |

The row's second line carries the finer state, such as `checking` or
`runner gone`.

D8. Every row starts with a grey type marker, an icon and the word Run,
Flow or Panel, before its status chip. A flow's task runs and a panel's
member runs are nested under the flow or panel row, in Live and in
Finished, each run keeping its own controls such as Open terminal.

D9. Finished has three filter dropdowns: Type (all, Run, Flow, Panel),
Status (all, Done, Incomplete, Failed) and Engine (all, Codex, OpenCode,
Claude; a flow or panel matches when any of its workers used that engine).
Its Clear button prunes the ended records the filters show, with their
logs and the records of their nested runs, after a confirmation that
lists them and every unmerged branch with the command that removes it.
It deletes no branch (E1).

D10. A click in a tray menu that a change made stale while it was open
triggers the item that was clicked (P26). GNOME's tray extension sends the
menu's `closed` event and the item's `clicked` event as two D-Bus
messages, `closed` first. Ember rebuilds a stale menu, deleting its
items, on the event-loop turn after `closed`.

D11. `RunCommandDialog` (`src/ember/app/widgets.py`) opens wide enough
for its whole window title and tall enough for every line of its wrapped
text and its command at that width, in the light and dark themes and at
fractional display scales. Its selectable command label draws no line,
frame or leftover paint around it, as A5 requires for selectable labels on
every screen (P27).

D12. `emb deps` and the Dependencies screen build the update command for
Codex, OpenCode and Claude Code from the install method found on the
machine, not from one fixed command per tool (P28, P29):

- Ember resolves the tool's executable, following symlinks, on the app's
  `PATH` and at the places it already searches outside `PATH`, such as
  `~/.opencode/bin`.
- Each component in `src/ember/data/components.toml` lists its install
  methods, each as a path pattern and an update command. The first method
  whose pattern matches the resolved path gives the command.
- The methods cover a global npm install under any prefix
  (`<prefix>/lib/node_modules/<package>`, giving
  `npm install -g --prefix <prefix> <package>@latest`), pnpm and Bun
  global installs, Homebrew, the vendor's own installer (its updater,
  named by full path), and a system package owned by dpkg.
- When the install folder is not writable by the owner, the command starts
  with `sudo`; it runs in the owner's terminal, and Ember itself runs no
  `sudo`.
- When no method matches, the component shows the resolved path, the
  tool's own updater by full path, and a line saying Ember could not tell
  how the tool was installed.
- Tests cover every listed method with temporary folder layouts.

D13. The help text of the Menu screen's Reviewer row (`ROLES` in
`src/ember/app/screens/menu.py`) names every place its choice applies:
read-only single runs, the reviewer of a flow whose plan and command name
none, and every gap check that names no reviewer, including the one
before a flow (P31). Which reviewer runs does not change.

## E. Records

Target release: 0.3.0.

E1. `emb prune --older-than <days> [--dry-run] [--json]` removes ended run,
flow and panel records and their logs older than the given age. It deletes
no branch: unmerged task, flow and run branches are listed with the command
that removes each.

## F. Skill

Target release: 0.3.0.

F1. Under "Owner answers" in `skill/references/gap-check.md`, the lead
checks the factual premise of each `high` gap against a live source, such
as a log, a rollout file or a record file, before putting the gap to the
owner. When the premise cannot be checked, the question to the owner says
so (P30).

## Tray busy cursor

Observed on 2026-11-02 with GNOME Shell 50.1 and the
`ubuntu-appindicators@ubuntu.com` extension from
`gnome-shell-ubuntu-extensions`.

- Ember's process ends about 0.2 seconds after Quit Ember is chosen in the
  tray menu. `stop()` waits for no background read at that point.
- Before passing a menu click to the app, the extension calls
  `ProvideXdgActivationToken` with the id of a launch sequence it opens with
  `global.create_app_launch_context()` (`dbusMenu.js` `_onActivate`,
  `appIndicator.js` `provideActivationToken`).
- The extension closes that sequence only when the D-Bus call fails. A
  click that opens no window, or an app that leaves the bus, leaves the
  sequence open until GNOME's launch timeout, and the busy cursor shows
  until then.
- Neither the StatusNotifierItem interface nor the Wayland activation
  protocol lets an app end a launch sequence without showing a window.

## Not planned

- A writer or reviewer per task in a flow plan (P6).
- Claude subagent panel members, and per-member spend in the panel summary
  (P7).
- An arm64 package and an apt repository (P10).
- Skill evals in `make check` or CI (P11).
